# 满配掉帧根治调研:机会式写入(isBusy 门控)——业界标杆 SdFat 解法

日期：2026-07-08
状态：**找到根治方向。当前"死等 PROGRAMMING"是掉帧根因;业界标杆 SdFat 用 isBusy() 门控的
机会式写入根治此问题。U5 SDMMC 有等价硬件位 SDMMC_FLAG_BUSYD0,方案可落地。待实现+A/B。**

## 0. 一句话结论

掉帧不是带宽不够(690KB/s vs 8MB/s),是**我们的 SD 写"死等卡 PROGRAMMING"**:每次 f_write
后 `while(cs==PROGRAMMING) vTaskDelay(1)` 把 logger 卡住,drain 串行堆积,低优先级/无FIFO 通道
的环溢出。业界高速 SD 日志标杆 **Bill Greiman 的 SdFat** 用完全不同的写法根治:
**写前查 `card->isBusy()`,卡忙就跳过不写、数据继续进环,只在卡空闲的间隙写** → CPU 永不
花在等卡上 → 阻塞从 40+ms 降到微秒级。U5 SDMMC 有硬件位 `SDMMC_FLAG_BUSYD0`(D0 忙信号线
的反值)可非阻塞查忙,是 isBusy() 的直接等价物 → **方案可落地。**

## 1. 当前架构 vs SdFat(决定性差异)

| 要素 | SdFat(标杆) | 我们现在 | 差距 |
|---|---|---|---|
| **忙检测** | 写前 `isBusy()`,忙则跳过不阻塞 | **死等** `while cs==PROGRAMMING vTaskDelay(1)`(sd_diskio.c:266) | ★根因 |
| 写粒度 | 每次 1 扇区(512B),写时间有界 | 一次 16/64KB(阻塞更长) | 次要 |
| 预分配连续文件 | `preAllocate` 避免写时长 FAT | f_expand 已回退(掉电损坏风险) | 已排除 |
| 环缓冲 | RingBuf ~50ms | 已有多环 | 已具备 |
| 元数据 | 全程不碰 FAT,末尾 truncate+sync | 每 1MB f_sync 一次 | 可接受 |

**根因锁定**:实测第三次所有环 hwm=100%(全满),H3/QMA/MIC 溢出。不是某环偏小,是**全局
drain 被"死等 PROGRAMMING"拖慢**,追不上产出。这与调研主结论(PROGRAMMING-bound)一致,
但 SdFat 揭示了破法:**不要等,机会式写。**

## 2. SdFat 机会式写入的四要素(权威解法,来源 ExFatLogger/TeensySdioLogger)

1. **isBusy() 门控(核心)**:`if (!sd.card()->isBusy()) { 写一扇区 }`。卡忙就**根本不发起写**,
   直接返回,数据继续攒环,下轮再试。从不在写上阻塞。卡忙(GC/PROGRAMMING)期间 CPU 全用于
   收数据,不浪费。
2. **单扇区写**:每次只写 512B,`MAX_WRITE=512`。写时间有界、可预测,不会一次长阻塞。
3. **连续预分配**:`preAllocate` 让簇链先建好,写时不长 FAT。(我们 f_expand 回退过,因掉电
   损坏;但可探索"预分配 + 更勤 sync"或分段小预分配折中。)
4. **环 ~50ms 深**:吸收卡的偶发长内部操作。溢出则计 overrun 不阻塞。

## 3. U5 落地可行性(硬件确认)

- `SDMMC_FLAG_BUSYD0`(stm32u5xx_ll_sdmmc.h:706)= "Inverted value of SDMMC_D0 line (Busy)"
  → 纯电平读,非阻塞、零命令开销,直接等价 SdFat 的 isBusy()。
- `__HAL_SD_GET_FLAG(&hsd1, SDMMC_FLAG_BUSYD0)` 即可查。
- 也有 `HAL_SD_GetCardState`(发 CMD13),但那个要发命令较慢,BUSYD0 更优。

## 4. 落地方案(渐进,每步可 A/B、可回退)

### 方案 A(最小改动,先验证机会式思路)—— logger 层机会式门控
在 logger drain 循环里,**每次 LoggerDrainRing 之前**查 `SDMMC_FLAG_BUSYD0`:卡忙则本轮跳过
所有写(数据继续进环),`osDelay` 短让出后重试;卡空闲才 drain。
- 优点:改动集中在 logger + 一个 isBusy 辅助函数,不动 sd_diskio 写机制。纯轮询、零损坏。
- 缺点:当前 `SD_disk_write` 内部仍会等 PROGRAMMING(f_write 是阻塞的);要真正非阻塞,需
  确保发起写时卡是空闲的,写完那一下 PROGRAMMING 短(单扇区/小块)。故需配合"写前必空闲 +
  小块写",让每次 f_write 的 PROGRAMMING 等待变短。

### 方案 B(更贴 SdFat)—— 单扇区机会式
FLUSH 改回小块(512B~4KB),逻辑:环里够一块 且 卡空闲 → 写一块;否则跳过。写粒度小 →
每次 PROGRAMMING 短 → 更快轮转所有通道。牺牲大块摊薄开销,但换来低延迟轮转。需 A/B 比较
"大块摊开销" vs "小块低延迟"哪个净掉帧低(③ 已证大块 64KB 有效,但仍死等)。

### 方案 C(结构性,最彻底)—— 重构 SD 写为非阻塞状态机
发起单扇区写后立即返回,不等 PROGRAMMING;下次进来先查 BUSYD0,空闲才发下一扇区。logger
变成"喂一扇区就走"的状态机。最接近 SdFat,但改动最大(要重写 sd_diskio 写路径 + logger)。

## 5. 风险与诚实标注

- isBusy 门控**不增加带宽**,而是**消除 CPU 等卡的浪费**,让 drain 在卡空闲间隙高效轮转。
  若卡的 GC 停顿总时长本身就超过"产出需要的写时间预算",仍会掉帧——但实测带宽余量 10x,
  瓶颈是等待而非带宽,故机会式预期能大幅改善。
- 单扇区写会**增加写次数/命令开销**(与 ③ 的"大块摊开销"相反)。需 A/B 找平衡点:可能是
  "中块(4-16KB)+ isBusy 门控"的组合最优。
- 预分配(要素3)我们回退过(掉电半提交 FAT → 整盘损坏)。**本方案先不碰预分配**,只上
  isBusy 门控 + 写粒度调整,规避那个坑。
- 需实测:isBusy 门控 + 写粒度,满配96k长录≥30min,数 [Ring] drop。不拍脑袋报数。

## 6. 建议下一步
先做**方案 A**(改动最小、验证机会式门控是否显著降掉帧):加一个 `SD_IsCardBusy()` 读 BUSYD0
的辅助,logger drain 前门控。若有效,再按 A/B 决定是否细化到 B/C 或调写粒度。

## 7. ★ 方案 A 实测结果:【无效,反效果】(2026-07-09)

同配置满配96k长录 A/B(逐 ring 写前 SD_IsCardBusy 门控):

| 通道 | ③ 门控OFF(23-16, 32.5min) | ④ 门控ON(00-41, 34.4min) |
|---|---|---|
| H3 | 13.21% | **15.28%**(更差) |
| QMA | 19.11% | **21.87%**(更差) |
| MIC | 29.5% | **35.6%**(更差) |
| writes | 112947 | 123674(更多、更碎) |

**结论:机会式门控在"满配持续高压"场景无效,甚至反效果。** 根因分析:
- SdFat 的 isBusy 门控有效,前提是**卡有明显空闲间隙**(中低采样率,写完一批有富余时间等下一批)。
- 我们是**满配持续 690KB/s 高压,卡几乎一直忙**(PROGRAMMING 接连不断)。门控在这种场景下
  只是**频繁 break + osDelay(2ms) 空转让出**,等于给 drain 强行插入大量空闲 → drain 总有效
  时间反而变少 → 掉帧更多、写更碎(writes 112k→124k)。
- **本质**:门控解决的是"CPU 不该花在等卡上",但我们的 CPU 本来就在 vTaskDelay(1) 让出、
  没浪费在 spin;真瓶颈是**卡的写吞吐(含 PROGRAMMING)在满配下就是不够快**——这不是调度
  能省出来的,是物理写入速度 vs 产出速率的差。**带宽余量 10x 是峰值误导,持续写入时卡的
  有效吞吐(被 PROGRAMMING/GC 拉低)才是真天花板。**

## 8. ★★ 决定性诊断(2026-07-09):真根因 = 写太碎 → PROGRAMMING 次数暴涨

从第三次(FLUSH64K)数据反推,拍死了"带宽 vs 调度"之争:
- 实际落盘 1298MB / 1953s = **649KB/s**;writes=**112947** 次。
- **纯数据传输只占 8.3% 时间**(162s @8MB/s);**91.7% 时间耗在 PROGRAMMING 等待**。
- **每次写平均仅 11.2KB(22.5 扇区),远小于 FLUSH 上限 64KB!** → 攒批根本没攒到位。

**这不是带宽瓶颈(传输才占 8%),是"写命令次数太多、每次都付固定 PROGRAMMING 开销"。**
每次写的 PROGRAMMING 等待≈固定成本,与写多少无关;写 112947 次 → 91.7% 时间在等。
**减少写次数(每次写更大块)→ PROGRAMMING 总时间直降 → 有效吞吐上升 → 掉帧降。**

### 为什么平均写只有 11KB(三个叠加的碎片化来源)
1. **环绕截断(最大元凶)**:`RingBuf_PeekContiguous` 只返回"到环尾的连续段"
   (`span = wr>rd ? wr-rd : size-rd`),rd 接近环尾时一次只拿到几 KB → wrap 处强制小写。
2. **小环半满 override**:H3(16K)/QMA(32K) 永远达不到 64K min_flush,总靠"半满"触发,
   每次仅写 8-16KB。
3. **round-robin 每环写一次就轮走**:不把一个环榨干,块更碎。

### 可解方向(都减写次数,纯轮询零损坏,不降采样率)
- **F1 消除环绕截断**:peek 到环尾后,若数据未取完,memcpy 分两段拼进 bounce 一次写(处理
  wrap),或写完环尾段立即接着写环首段(合并成逻辑大块)。直接砍掉来源1。
- **F2 榨干单环**:一个环只要有数据就连续写到空/写够大块,再轮下一个(而非每环一次)。
- **F3 提高小环 min_flush 有效性**:小环也攒到"接近满环"再写(如 size*3/4),减少小写。
  代价:小环延迟略升、峰值略高,但小环负载低(H3 14KB/s、QMA 57KB/s)风险小。
- **F4 bounce 更大 + 跨环合并**:极限做法,把多个环数据合并成一次超大写(改动大,先不做)。

**建议先做 F1+F3(对症、改动小)**:F1 修环绕截断(平均写块大小应从 11KB 大幅回升到接近
64KB),F3 让小环攒够再写。预期把 writes 从 112947 大幅降低 → PROGRAMMING 时间降 → 掉帧降。
方案 A(门控)已证无效,APP_SD_OPPORTUNISTIC 设 0 回退。

## 9. ★★★ 最终结论(2026-07-09):卡持续写吞吐 ~648KB/s 是物理天花板

F1+F3 实测(⑤ CTBX_01-59, 42.5min)对比 ③(FLUSH64K):

| 指标 | ③ FLUSH64K | ⑤ F1+F3 | 说明 |
|---|---|---|---|
| avg 写块 | 11.2KB | **13.3KB** | F1 确实增大了写块 ✓ |
| 写速率 | 58/s | **49/s** | F1 确实减少了写次数 ✓ |
| **落盘率** | **649KB/s** | **648KB/s** | ★纹丝不动 |
| 掉帧 H3/QMA/MIC | 13/19/29% | 11/18/32% | 同档,无实质改善 |

**F1 生效了(写更大更少),但落盘率锁死在 ~648KB/s。这就是这张卡的持续写入物理天花板
(含卡内部 flash 编程/GC 的极限速度,与 SPI 总线 8MB/s 无关)。** 满配产出 690KB/s > 648,
缺口 ~42KB/s(6%)注定要丢,LSM(先drain/High)吃饱,QMA/H3/MIC 按序承担缺口。

**修正此前所有误判**:传输占 8.3% 不代表卡闲——那 8.3% 是纯 SPI 传输,卡的内部编程才是瓶颈。
调度/攒批/大块/门控都动不了卡的内部编程速度。**代码层面到此为止,已到物理极限。**

**仅剩两条真出路(无第三条):**
1. **降产出到 648 以下**:BIN 格式(690→517KB/s,低于卡上限 → 掉帧应清零,不降采样率!)
   或降 MIC 96→48k(省94KB/s→596)或降 QMA ODR。
2. **换更快的卡**:持续写 >690KB/s 的 UHS-I U3/A2 或工业级卡(零代码)。

★ BIN 格式是最优解:517KB/s 远低于 648 天花板,理论上掉帧清零,且**采样率一点不降**、
工程已支持(output_format 配置切换)。代价仅"数据需 BIN 解析工具,不能直接看文本"。

## 10. ★★★ 新假说(2026-07-09,更深):648KB/s 不是卡极限,是"7 文件交织写"退化成随机写

**质疑 §9 的"物理天花板"结论**:648KB/s 对现代 SD 卡低得反常——Class10/U1 标称持续写 ≥10MB/s,
我们只有 6.5%。反推:若全 32KB 满块写,每块 49ms 中 **45ms 是 PROGRAMMING**(传输仅 4ms)——
顺序多块写的 PROGRAMMING 应是几 ms,45ms 高得离谱。

**新根因假说**:我们**同时向 7 个文件写**(ACC_LOW/GYR_LOW/QMA/H3/MIC/ENV/MAG),它们在卡上是
7 个分散的物理区域。drain 循环轮流写 A 一块、B 一块…… 对 SD 卡 FTL(闪存转换层)这是
**7 路随机写交织,不是顺序写**:
- 每切文件 → 写到卡不同 flash 区域 → FTL 维护多个擦除块 → 写放大 + 频繁 GC。
- SD 卡的高速多块写(→10MB/s)**只在连续顺序写同一区域**才有;交织写打回随机写性能(几百 KB/s,
  正好对上实测 648)。
- 原理佐证:"random writes substantially increase garbage collection cost and reduce throughput"
  (NSF/write-amplification 文献)。簇=32KB 也确认 FatFs 每次 disk_write 被簇边界截到 ≤32KB。

**若假说成立 → 648 不是物理天花板,是访问模式问题 → 可解且不必降采样率/换卡!**

### 验证与解法(按成本排序)
- **V1 最省验证(改配置,不改码)**:临时只开 1-2 个高速传感器(如仅 LSM,写 2 文件),满配长录,
  看落盘率是否远超 648。若飙升 → 坐实"多文件交织"是真凶。(注意:这改了负载,非纯变量,但
  若落盘率从 648 跳到 数MB/s,信号足够强。)
- **S1 单文件合并写(治本,改动中)**:7 路数据合并写进**一个** .bin 文件(每条记录带通道 ID +
  timestamp),下游用工具拆分。SD 卡看到的是**单一顺序写流** → 高速多块写生效 → 吞吐可能 10x。
  这是高速多传感器 logger 的标准架构(SdFat/黑匣子都这么做)。代价:数据需工具拆分。
- **S2 减少并发文件**:合并同源(LSM acc+gyr 本可合一文件;温湿度+磁力低速可合并),从 7→3-4,
  减轻交织。折中。
- **BIN 格式(§9)**:降产出 25%,与本假说正交,可叠加。

**★ 关键:先做 V1 验证假说(最省)。若坐实,S1 单文件合并写是真正根治且不降采样率的解。**
这比"降采样率/换卡"高一个层次——因为它说明卡本来够快,是我们用法废了它。

### ★★★ 2026-07-09 满配 V2 判别实验结果:交织假说被证伪,648KB/s 确为真实持续写上限

前两次 V1/V2 都因 DEVCFG.JSN 只开了 accel_low 而误测成 LSM-only,无效。这次把 accel_high/
accel_mid/mic/env/mag 全 enabled=1 恢复满配,APP_SD_V2=1U(7 路全部强制写进单文件 idx0,
总产出满配 690KB/s 不变,文件数 7→1,隔离"交织 vs 顺序"为唯一变量),长录 ≈1378s(≈23min):

```
writes=70861 dma_err=0 retry=0 sem_to=0 prog_to=0 fail=0
[Ring] lsmA drop=0 hwm=163839/163840 | lsmG drop=0 hwm=98303/98304
     | h3  drop=1393833  hwm=16383/16384
     | qma drop=7888247  hwm=32767/32768
     | mic drop=24930304 hwm=195584/196608
```

**判读:单文件顺序写下(交织被彻底消除),h3/qma/mic 照样重丢。→ 交织/FTL 随机写假说死。**
§10 上半段的"648 是访问模式问题、可软件根治"结论**错误**。648KB/s 是卡真实的持续写吞吐上限,
与文件如何排布无关。S1 单文件合并写**不能**解决掉帧(已被本实验前瞻性否决,不必再实现)。

**为什么 LSM 零丢、qma/h3/mic 全丢?** 不是通道特殊,是 drain 轮询顺序 LSM_ACC→LSM_GYR→QMA→
H3→MIC→… 队首的 LSM(大 ring+High 优先级)每轮先吃满带宽,卡触顶后队尾的 qma/h3/mic 被饿死。
这解释"谁丢"但改不了总量缺口。

**最终仅剩两条真出路(与 §9 一致,已由本实验确认):**
1. 降产出:BIN 格式 690→517KB/s(帧 22B/条),或降 mic 采样率。data-value 取舍归用户。
2. 提吞吐:换更快 SD 卡 / 提 SDMMC 时钟 / 双 SDMMC 双卡分流(硬件路)。

无任何软件调度技巧能凭空补上 ~40KB/s 物理缺口。测毕 APP_SD_V2 已回退 0U(混写数据不可留用)。
