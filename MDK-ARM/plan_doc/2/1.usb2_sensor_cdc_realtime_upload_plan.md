# USB2.0 实时上传传感器数据实现与测试计划书

## 1. 需求理解

目标是在当前 `STM32U575 + FreeRTOS + 三传感器` 工程上，实现通过 Type-C 接口把传感器数据实时上传到电脑端。

本方案默认使用：

- `PA12 -> USB_DP / USB_P`
- `PA11 -> USB_DM / USB_N`
- STM32U575 内置 `USB OTG FS Device`
- USB 设备类第一版采用 `CDC ACM`，在电脑端表现为一个虚拟串口

需要先说明一个关键点：当前 `PA11/PA12` 直连的是 STM32 内置 USB FS PHY，所以这里的“USB2.0 通信”实际能力是 USB 2.0 Full-Speed，也就是 `12Mbps`，不是 High-Speed `480Mbps`。如果未来必须做到 480Mbps，需要外部 ULPI HS PHY 或更换带 HS PHY 的硬件方案，当前原理图路线不支持直接跑 HS。

## 2. 当前硬件判断

### 2.1 Type-C 角色

从你给的 Type-C 原理图看：

- `CC1` 通过 `5.1K` 下拉到 GND
- `CC2` 通过 `5.1K` 下拉到 GND
- 这符合 USB Type-C `UFP / Device` 设备角色
- 电脑作为 Host，板子作为 USB Device，是正确方向

### 2.2 USB 数据线

原理图连接为：

- Type-C `DP1/DP2` 合并后接 `USB_P`
- Type-C `DN1/DN2` 合并后接 `USB_N`
- MCU 管脚图中：
  - `PA12 = USB_P / DP`
  - `PA11 = USB_N / DM`

软件配置应使用 `USB_OTG_FS` 外设，GPIO 复用为 `GPIO_AF10_USB`。

### 2.3 VBUS 与 KEY_ADC 检测

根据补充的电源/按键检测原理图，`KEY_ADC` 这一路确实可以作为应用层的 `VBUS present` 检测来源。

硬件路径可以理解为：

- `VBUS` 经过 `D6 BAT54H` 汇入检测节点
- `VBAT + KEY` 经过 `D2 BAT54H` 汇入同一检测节点
- `POWER_CTL` 经过 `D3 BAT54H` 汇入同一检测节点
- 检测节点再经过 `R9=47K / R11=47K` 分压后进入 `KEY_ADC`
- 同一检测节点还通过 `C16` 和 `Q3 2SK3018` 影响 `PMOS_SW`

所以这一路不是单纯的 USB VBUS 直连 GPIO，而是一个“电源/按键/控制信号 OR 后再分压”的 ADC 检测网络。理论上 ADC 端电压大致满足：

```text
KEY_ADC ≈ (输入源电压 - BAT54H 正向压降) / 2
```

按常见电压估算：

- Type-C 插电脑，`VBUS=5V` 时，`KEY_ADC` 约在 `2.2V ~ 2.4V`
- 电池或按键相关路径接近 `4.2V` 时，`KEY_ADC` 约在 `1.9V ~ 2.1V`
- 其它 `3.3V` 控制路径触发时，`KEY_ADC` 约在 `1.5V ~ 1.6V`

因此软件上可以用 `KEY_ADC` 判断是否检测到 USB VBUS，但要做成 ADC 区间判断，而不是普通 GPIO 高低电平判断。

这里还要区分两件事：

1. `KEY_ADC` 可以作为应用层的 VBUS 检测输入，用来决定是否启动 USB Device、是否进入 USB 上传状态、是否打印插拔日志。
2. `KEY_ADC` 不是 STM32 USB 外设专用的硬件 VBUS sensing 引脚，不能直接让 USB 外设自动完成 VBUS sensing。

因此第一版软件策略更新为：

- `hpcd_USB_OTG_FS.Init.vbus_sensing_enable = DISABLE`
- 新增 `KEY_ADC` 采样与区间判定，得到软件层 `vbus_present` 状态
- USB Device 栈可以常驻初始化，也可以在 `vbus_present` 稳定后启动
- 第一阶段建议先常驻 USB Device 栈，用 `KEY_ADC` 做插拔状态观测和日志
- 等 CDC 枚举稳定后，再评估是否改成由 `KEY_ADC` 控制 USB Device start/stop

当前工程的 `Core/Src/usb_otg.c` 已经关闭硬件 VBUS sensing，这一点仍然是正确的；后续需要补的是 `KEY_ADC` 的 ADC 驱动和阈值校准。

### 2.4 需要实物确认的硬件项

实施前建议用万用表/示波器确认：

1. Type-C 插电脑后 `VBUS` 是否稳定约 `5V`。
2. MCU `VddUSB` 供电是否已使能，软件中已有 `HAL_PWREx_EnableVddUSB()`。
3. `PA12/PA11` 没有被其它外设复用或占用。
4. D+/D- 没有接反：枚举失败且电脑完全无反应时，优先检查这一项。
5. Type-C 未插、Type-C 已插、按键按下、电池供电等状态下，`KEY_ADC` 的实测 ADC 原始值分别是多少。
6. `KEY_ADC` 的 VBUS 档位是否能和按键/VBAT/POWER_CTL 档位稳定区分。
7. 如果板上没有 USB ESD 保护和 22R 串联电阻，短线调试通常可跑通，但量产版建议补齐。

## 3. 当前工程基础

结合当前代码，已经具备以下基础：

- `Core/Src/usb_otg.c`

  - 已使能 `USB_OTG_FS` 时钟与 `VddUSB`
  - 已关闭 USB 外设硬件 VBUS sensing，后续由 `KEY_ADC` 做应用层检测

  - 已定义统一快照结构 `AppSensorSnapshot_t`

当前还缺少的是：

- 一个独立的 USB 上传任务或发送队列
- 电脑端接收测试脚本

## 4. 推荐总体方案

第一版采用 `USB CDC ACM`：

- 板子枚举为虚拟串口
- 电脑端使用串口工具或 Python 脚本读取
- 传感器数据先用 CSV 行上传，便于人工检查
- 稳定后再增加二进制帧格式，提高吞吐和可靠性

不建议第一版直接做自定义 Bulk/WinUSB，原因是：

- Windows 端驱动和工具链更复杂
- 首次 bring-up 难以快速判断问题在固件、描述符、驱动还是上位机
- CDC 足够覆盖当前 `500ms` 周期的三传感器数据上传

## 5. 软件架构

### 5.1 任务划分

建议新增一个独立任务：

- `usbUploadTask`
- 优先级：`osPriorityNormal`
- 栈大小：建议 `1024 * 4` 起步
- 上传周期：第一版默认 `500ms`，但建议单独定义 `APP_USB_UPLOAD_PERIOD_MS`，不要与 `APP_SENSOR_SAMPLE_PERIOD_MS` 硬绑定

任务职责：

1. 判断 USB 当前是否已处于“可发送”状态。
2. 周期性复制 `AppSensorSnapshot_t`。
3. 将快照格式化为 CSV 行。
4. 调用 CDC 发送接口。
5. 当 USB 未连接、串口未打开或发送忙时，不阻塞传感器采样任务。

建议实现时不要把“USB 已枚举”和“电脑端已打开串口”混为一个条件，而是至少区分三类状态：

- `USB configured`：USB 已完成枚举并进入 Configured
- `CDC terminal open`：电脑端串口工具已真正打开 COM 口，可通过 DTR / `SET_CONTROL_LINE_STATE` 辅助判断
- `USB ready`：满足当前允许发送的最终条件

建议后续在 `usbd_cdc_if.c` 中提供：

- `uint8_t USB_CDC_IsConfigured(void)`
- `uint8_t USB_CDC_IsTerminalOpen(void)`
- `uint8_t USB_CDC_IsReady(void)`

第一版最小 bring-up 阶段可以只依赖 `USB configured`，而在 CSV 实时上传阶段建议再叠加 `CDC terminal open` 条件，这样更符合 PC 端实际使用行为。

### 5.2 数据流

推荐数据流如下：

```text
LSM6DSOX task       \
H3LIS100DL task      -> AppSensorSnapshot_t -> usbUploadTask -> USB CDC -> PC
QMA6100P task      /
```

第一版不让传感器任务直接调用 USB 发送，避免 USB 发送忙、电脑断开、枚举失败等问题反向影响采样任务。

### 5.3 建议增加 USB 应用层状态机

为了避免后续把 `vbus_present`、枚举状态、串口打开状态、发送状态分散在多个布尔变量里，建议应用层从第一版起就显式维护一个轻量状态机。可以先不做得很复杂，但至少建议覆盖：

```text
DETACHED -> ATTACHED -> CONFIGURED -> OPEN -> STREAMING
```

其中可对应理解为：

- `DETACHED`：软件判定当前未接入 USB
- `ATTACHED`：检测到 VBUS 或物理接入迹象，但尚未完成枚举
- `CONFIGURED`：USB Device 已完成枚举并进入 Configured
- `OPEN`：PC 端串口工具已打开 COM 口
- `STREAMING`：系统已实际开始稳定发送 CSV 数据

这样做的好处是：

1. 插拔日志更清晰。
2. 便于定位问题卡在“未检测到插入 / 未枚举 / 已枚举未打开 / 已打开未发送”的哪一层。
3. 以后如果让 `KEY_ADC` 参与 USB start/stop，也容易接入。
4. 压力测试和异常恢复时更容易判断恢复到哪一步。

第一版即使不把它做成完整公共模块，也建议至少在 `usbUploadTask` 或 USB 管理代码中统一维护状态变量，避免各处零散判断。

### 5.3 与 SD 日志任务的关系

USB CDC 实时上传和 SD 日志写入可以并行存在，因为 CDC 不直接访问 SD 卡，不会出现 MSC 那种“电脑和本地 FatFs 同时访问同一张卡”的互斥问题。

第一版建议：

- 保留当前 `loggerTask`
- 新增 `usbUploadTask`
- 两者都从 `AppSensorSnapshot_t` 读取快照
- 共同使用 `snapshot_mutex`

如果后续 USB 上传频率提高到高采样率，应再引入环形缓冲区，而不是一直格式化 CSV。

## 6. 数据协议

### 6.1 第一版 CSV 文本协议

第一版推荐每帧一行 CSV，以 `\r\n` 结束。

表头建议在“电脑端串口真正打开后的本次会话首次发送前”发送一次，而不是只要枚举完成就立即发送。这样可避免 PC 端串口工具尚未打开时把表头提前发掉，导致后续只看到数据行、看不到列名。

推荐策略：

1. `CDC terminal open` 从 `0 -> 1` 时，清零本次会话的 `header_sent` 标记。
2. 本次会话第一次成功发送数据前，先发送 CSV 表头。
3. USB 断开、重新枚举或串口关闭后，下次重新打开串口时再次发送表头。

表头建议设备连接后先发送一次：

```text
tick_ms,row_seq,lsm_valid,lsm_age_ms,lsm_ax_mg,lsm_ay_mg,lsm_az_mg,lsm_gx_mdps,lsm_gy_mdps,lsm_gz_mdps,lsm_temp_c,h3_valid,h3_age_ms,h3_raw_x,h3_raw_y,h3_raw_z,h3_ax_mg,h3_ay_mg,h3_az_mg,qma_valid,qma_age_ms,qma_raw_x,qma_raw_y,qma_raw_z,qma_ax_mg,qma_ay_mg,qma_az_mg
```

数据行示例：

```text
123456,18,1,20,1.2,-3.4,1001.5,0.0,1.1,-0.8,27.5,1,18,12,-8,999,120.0,-80.0,9990.0,1,15,3,4,1024,30.0,40.0,1024.0
```

优点：

- 串口助手可直接看
- Python 可直接保存 CSV
- 和当前 SD CSV 日志格式容易对齐

### 6.2 第二版二进制帧协议

当需要更高吞吐时，再切换或并行支持二进制帧：

```text
SOF(2) + version(1) + type(1) + seq(4) + tick_ms(4) + payload_len(2) + payload + crc16(2)
```

建议：

- `SOF = 0xA5 0x5A`
- 小端序
- `type=0x01` 表示传感器快照
- `type=0x02` 表示状态/错误信息
- `crc16` 覆盖 `version` 到 `payload` 末尾

二进制协议不作为第一阶段目标，只作为后续吞吐优化预留。

## 7. 固件实施步骤

### 阶段 0：KEY_ADC VBUS 检测确认

目标：先把补充原理图里的 `KEY_ADC` 检测链路实测清楚，确认它能稳定区分 USB VBUS。

实施内容：

1. 打开 `HAL_ADC_MODULE_ENABLED`。
2. 新增 `adc.c / adc.h` 或按当前工程风格新增 `key_adc.c / key_adc.h`。
3. 配置 `KEY_ADC` 对应 ADC 通道，先使用轮询采样即可。
4. 启动后周期性打印 ADC 原始值和换算电压。
5. 分别记录以下状态的 ADC 值：
   - Type-C 未插
   - Type-C 插电脑，`VBUS=5V`
   - 按键按下
   - 电池供电或 VBAT 路径有效
   - `POWER_CTL` 路径有效
6. 根据实测值定义区间阈值和迟滞，例如：
   - `KEY_ADC_VBUS_MIN`
   - `KEY_ADC_VBUS_MAX`
   - `KEY_ADC_FILTER_COUNT`
   - `KEY_ADC_VBUS_ENTER_MIN/MAX`
   - `KEY_ADC_VBUS_EXIT_MIN/MAX`
7. `KEY_ADC` 判定逻辑建议固定采用：
   - 区间窗口判断，不使用单阈值
   - 连续多次命中后才置位 `vbus_present`
   - 连续多次离开后才清位 `vbus_present`
   - 进入阈值与退出阈值分离，形成迟滞，避免插拔边沿抖动
8. 提供软件接口：
   - `uint8_t KeyAdc_IsVbusPresent(void)`
   - `uint16_t KeyAdc_GetRaw(void)`
   - `uint32_t KeyAdc_GetMillivolt(void)`

验收标准：

- 插入 Type-C 后，`KeyAdc_IsVbusPresent()` 能稳定变为 `1`。
- 拔出 Type-C 后，`KeyAdc_IsVbusPresent()` 能稳定变为 `0`。
- 按键/VBAT/POWER_CTL 不会被误判为 USB VBUS。
- ADC 检测不影响当前传感器任务和 SD 日志任务。

### 阶段 A：USB CDC 最小枚举

目标：电脑插入 Type-C 后，能识别出一个虚拟串口设备。

实施内容：

1. 引入 ST `STM32_USB_Device_Library/Core`。
2. 引入 ST `STM32_USB_Device_Library/Class/CDC`。
3. 新增 `Core/Inc/usb_device.h`、`Core/Src/usb_device.c`。
4. 新增 `Core/Inc/usbd_conf.h`、`Core/Src/usbd_conf.c`，桥接当前 `hpcd_USB_OTG_FS`。
5. 新增 `Core/Inc/usbd_desc.h`、`Core/Src/usbd_desc.c`。
6. 新增 `Core/Inc/usbd_cdc_if.h`、`Core/Src/usbd_cdc_if.c`。
7. 在 `main.c` 中从 `MX_USB_OTG_FS_PCD_Init()` 过渡到 `MX_USB_DEVICE_Init()`，避免 PCD 被重复初始化。
8. 第一版 USB Device 栈可常驻启动，不强依赖 `KEY_ADC` 控制 start/stop。
9. 明确保留 `usb_otg.c` 中已经验证过的 MSP/GPIO/时钟/VddUSB 配置思路，避免在 `usb_otg.c` 与 `usbd_conf.c` 两边都做完整 PCD 初始化。
10. 在状态日志中打印 `KEY_ADC` 的 `vbus_present`，用于对照 USB 枚举状态。
11. 将新增源文件加入 `SensorProj.uvprojx` 与 `.eide/eide.yml`。

验收标准：

- Windows 设备管理器出现 `USB Serial Device (COMx)` 或自定义 CDC 设备。
- 插拔 10 次，不能 HardFault。
- 串口助手能打开该 COM 口。

### 阶段 B：CDC 发送最小字符串

目标：电脑端能收到 MCU 主动发送的字符串。

实施内容：

1. 在 `usbd_cdc_if.c` 中提供安全发送接口，例如：
   - `uint8_t USB_CDC_IsConfigured(void)`
   - `uint8_t USB_CDC_IsTerminalOpen(void)`
   - `uint8_t USB_CDC_IsReady(void)`
   - `uint8_t USB_CDC_TryTransmit(const uint8_t *buf, uint16_t len)`
2. 处理 `USBD_BUSY`，不在高优先级任务中死等。
3. 建议增加最小统计项，至少包括：
   - `tx_ok_count`
   - `tx_busy_drop_count`
   - `tx_not_ready_drop_count`
   - `tx_error_count`
4. 建议在 CDC 发送完成回调中只做轻量计数或状态更新，不做大块格式化和复杂逻辑，以便定位“首次发送后一直 `USBD_BUSY`”这类问题。
5. 新增 `usbUploadTask`，每 1s 发送一行测试文本：

```text
usb alive,tick=12345
```

验收标准：

- 串口助手可持续收到测试文本。
- 拔掉 USB 后系统仍继续运行，传感器任务和 SD 日志不受影响。
- 重新插入后可恢复发送。

### 阶段 C：上传传感器 CSV 快照

目标：通过 USB CDC 实时上传三路传感器数据。

实施内容：

1. `usbUploadTask` 周期性调用快照复制接口。
2. 将快照格式化为 CSV 行。
3. 连接后发送 CSV 表头。
4. 每 `APP_USB_UPLOAD_PERIOD_MS` 发送一行数据，默认值可先设为 `500ms`。
5. 如果 USB 未连接、串口未打开或发送忙，丢弃本周期数据，不阻塞。

验收标准：

- 电脑端保存的 CSV 可用 Excel/Python 正常打开。
- CSV 中三颗传感器 `valid` 字段符合当前传感器状态。
- 运行 30 分钟无 HardFault、无明显任务卡死。

### 阶段 D：压力与异常测试

目标：验证 USB 连接异常、电脑端打开关闭串口、长时间运行时的稳定性。

测试项：

1. 上电前已插 USB。
2. 上电后再插 USB。
3. 运行中拔 USB。
4. 运行中反复插拔 USB。
5. 电脑端串口工具打开/关闭多次。
6. 电脑休眠或 USB 选择性挂起后恢复。
7. SD 卡写日志和 USB 上传同时运行 2 小时。

验收标准：

- 不 HardFault。
- 不影响传感器采样任务持续运行。
- USB 恢复后能继续输出。
- SD 日志文件仍可正常保存。

### 阶段 E：吞吐优化

当第一版 CDC CSV 稳定后，再考虑优化：

1. 上传周期从 `500ms` 降到 `100ms`、`20ms` 逐步测试。
2. 增加 CDC 发送环形缓冲区。
3. 将 CSV 改为二进制帧。
4. 用 PC 端脚本统计丢帧率、平均延迟、最大延迟。
5. 如果 CDC 满足不了目标吞吐，再评估 WinUSB/Vendor Bulk。

## 8. 电脑端测试方案

### 8.1 Windows 基础测试

工具：

- 设备管理器
- 串口助手
- Python 3 + `pyserial`

步骤：

1. 插入 Type-C。
2. 打开设备管理器，确认出现 COM 口。
3. 用串口助手打开 COM 口，波特率可任意设置，CDC 实际不依赖传统 UART 波特率。
4. 观察是否持续输出 CSV 行。

### 8.2 Python 保存 CSV

建议准备一个简单脚本：

```python
import serial
from datetime import datetime

port = "COM8"
baud = 115200
out = datetime.now().strftime("usb_sensor_%Y%m%d_%H%M%S.csv")

with serial.Serial(port, baudrate=baud, timeout=2) as ser, open(out, "wb") as f:
    while True:
        line = ser.readline()
        if line:
            f.write(line)
            f.flush()
            print(line.decode(errors="replace").rstrip())
```

验收：

- 生成的 CSV 行数持续增长。
- 无乱码。
- 无大量空行。
- 拔插 USB 后脚本报错属于正常，后续可再做自动重连版本。

## 9. 关键风险与处理策略

### 9.1 KEY_ADC VBUS 误判

`KEY_ADC` 同时接入了 VBUS、VBAT/KEY、POWER_CTL 三类来源，所以最大风险是把按键或其它电源状态误判为 USB 插入。

处理策略：

- 阈值必须以实板 ADC 原始值为准，不直接写死理论电压。
- VBUS 判断使用区间窗口，不使用单阈值。
- 增加连续多次采样确认和迟滞，避免插拔瞬间抖动。
- 第一版 USB Device 栈先常驻，`KEY_ADC` 只做状态观测；等枚举链路稳定后，再让它参与 USB start/stop 控制。

### 9.2 USB 枚举失败

优先排查顺序：

1. `PA11/PA12` 是否接反。
2. `GPIO_AF10_USB` 是否配置正确。
3. `USB_OTG_FS` 时钟是否为稳定 `48MHz`。
4. `VddUSB` 是否已使能。
5. 电脑端是否有设备插入提示。
6. 描述符长度、端点配置是否正确。

### 9.3 CDC 发送忙

不能在任务里无限等待 `USBD_BUSY`。

第一版策略：

- 忙则丢弃当前行
- 记录一个 `drop_count`
- 建议进一步区分：
  - `tx_busy_drop_count`
  - `tx_not_ready_drop_count`
  - `tx_error_count`
- 定期通过串口或 USB 状态行输出

后续策略：

- 增加环形缓冲区
- 独立 TX worker 消费队列

### 9.4 USB 断开导致系统卡死

所有 USB 发送接口必须满足：

- USB 未配置时立即返回失败
- 串口未被主机打开时立即返回失败
- 发送忙时立即返回失败
- 不在中断里格式化字符串
- 不在传感器任务里直接等待 USB
- USB ISR / callback 中只做状态置位、缓冲区状态更新或简短计数，不做大块 memcpy、复杂逻辑或互斥锁等待

### 9.5 CDC 与 SD 日志同时运行的负载

当前 `loggerTask` 会周期性 `f_write/f_sync`，USB 上传会周期性格式化字符串。

第一版采样周期 `500ms` 下负载很低，应可并行。若后续提高上传频率，需要关注：

- `snprintf` CPU 占用
- FreeRTOS 栈余量
- USB TX 发送队列积压
- SD 写入延迟造成的调度抖动

## 12. 推荐执行顺序

建议按下面顺序推进：

1. 先做 `KEY_ADC` 实测和 VBUS 阈值校准。
2. 再只做 USB CDC 枚举，不接传感器数据。
3. 再做固定字符串发送，确认 PC 接收链路。
4. 再接入 `AppSensorSnapshot_t`，上传 CSV。
5. 再做插拔、长稳、电脑端脚本保存，并对照 `KEY_ADC vbus_present` 与 CDC 枚举状态。
6. 最后再讨论是否需要二进制协议或 WinUSB。

这样每一步都有清晰可测的结果，遇到问题时也容易定位是硬件、描述符、USB 栈、RTOS 任务，还是电脑端工具的问题。
