# 上位机诊断：LSM 满速(6664Hz) USB 数据丢帧+乱序 —— 问题在"读取之后"的拼接

## 结论先行
- **USB 读取吞吐已达标**：上位机 LSM-BENCH 实测 **~370 KB/s ≈ 6650 帧/s**，等于 LSM 6664Hz 的满速产出。说明**设备没溢出、USB 传输层没丢、读取线程速率够**。
- **但落盘 CSV 仍丢 17.7% + 294 次 frame_id 倒退 + 撕裂行（出现 1 亿级乱 frame_id、年份乱码）**。
- 两者打架 → 瓶颈**不在 USB 读取**，而在**字节读下来之后的"拼接 / 行切分 / 落盘"环节**。请重点查这一段。

## 关键证据
1. **BENCH 6650 帧/s vs 落盘 5500 帧/s**：字节被拉下来了（BENCH 计数），但落地少了 ~17% → 丢在解析/落盘。
2. **294 次 frame_id 倒退**：设备是**单生产者、严格按 frame_id 递增**顺序发送的；USB Bulk 在**单端点上不会乱序**。CSV 里出现"后发的号排到前面"，只可能是上位机侧**多缓冲/多线程读取后没按序合并**。
3. **撕裂行**（5 位残缺 frame_id、`160101…`/`601101…` 乱码 datetime）：典型的**按固定块边界切行**导致跨块半行被丢/拼错。

## 两个根因（请对照自查）
### A. 没有按序拼接 → 乱序
LSM 这一路若用了**多个并发/overlapped IN 读**（为提吞吐），**回收时必须按提交顺序合并**到同一字节流，不能哪个先回来就先写。乱序回收 → 块错位 → frame_id 倒退。
- 修法：每个端点一个**单调有序的接收队列**；overlapped 读带序号，**按序号顺序消费**后再交给解析。

### B. USB 传输边界 ≠ CSV 行边界 → 丢行 + 撕裂
每个 bulk 传输回来的 buffer **不是整行对齐的**——一行 CSV 可能跨两个传输。若按"每个传输 buffer 单独切行、丢弃残尾"，就会**既丢行又产生撕裂行**（正好解释 17% 丢 + 撕裂同时出现）。
- 修法：把所有传输回来的字节**无缝追加**到一个**连续字节缓冲**，再统一按 `\n` 切行；**跨传输的半行要留到下一块拼上**，不能丢。

## 落盘前不要让解析阻塞读取
读取线程只负责"收字节 + 按序入队"，**解析/落盘放到另一线程**。否则 CSV 解析一慢就回压读取 → 设备侧双缓冲被覆盖 → 二次丢帧。

## 一步到位的验证方法
让上位机把**收到的原始字节流原样存一份**（完全不解析、不切行，纯 append 落 .bin），再离线对这份 .bin 按 `\n` 切行分析：
- **若原始 .bin 里 frame_id 连续无缺、无撕裂** → 100% 是上位机"解析/拼接/落盘"的 bug（按 A、B 改）；
- 若原始 .bin 里就缺就乱 → 才回到 USB 读取层（但 BENCH 已基本排除）。

## 固件侧结论（供参考）
- 设备**严格按 frame_id 递增、单端点顺序发送**，满速产满 6664；
- LSM 流路径（EP1=0x81、FIFO、双缓冲）与历史"3 传感器全速稳"版本**逐字节一致，无回归**；
- BENCH 已证明设备能被以 6650 帧/s 拉走 → 设备侧无需改动。
- 端点：LSM=`0x81`、H3=`0x82`、QMA=`0x83`、MIC=`0x84`、命令响应=`0x85`、命令下发=`0x01 OUT`。
